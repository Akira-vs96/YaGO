# YaGo

YaGo — учебное веб-приложение для Астаны, объединяющее на одной карте четыре городские услуги:

- заказ такси;
- доставка еды из заведений;
- аренда электросамокатов;
- аренда велосипедов.

Пользователь выбирает услугу, указывает адрес или объект на карте, оформляет заказ либо аренду и отслеживает выполнение. Исполнитель получает назначенный заказ, оператор управляет каталогом, транспортом, тарифами и геозонами, а администратор контролирует доступ и просматривает показатели системы.

Проект выполняется как командная учебная работа по [техническому заданию на 15 недель](TZ_15weeks_team_plan.md). Первые семь недель отведены анализу и проектированию, недели 8–15 — разработке, интеграции, проверкам, развёртыванию и защите.

## Статус проекта

Репозиторий содержит работающий прототип клиентской и серверной частей, а также материалы проектирования. Полный набор функций из ТЗ является целевым результатом 15-недельного плана; наличие схемы, миграции или описания в документации не означает, что соответствующая функция уже реализована.

В текущем прототипе доступны:

- React-интерфейс на Vite;
- FastAPI API;
- PostgreSQL и SQL-миграции базовой схемы;
- каталог заведений и меню;
- создание заказов и переходы их статусов;
- расчёт маршрута через OSRM;
- поиск и обратное геокодирование через Nominatim;
- передача событий заказа и позиции исполнителя через WebSocket;
- восстановление актуального состояния через REST после переподключения;
- начальная ER-модель в третьей нормальной форме.

Целевые функции проекта включают полноценные роли и RBAC, доставку, такси, аренду техники, QR-эмуляцию, геозоны, тарификацию с сохранением версии тарифа, отзывы, администрирование и аналитику. Оплата, физический замок, двухфакторное подтверждение и проверка студенческого статуса в учебной версии могут быть эмулированы.

### Клиентская часть

Клиент реализован на React и Vite. Для карты используется Leaflet. HTTP-запросы получают начальное состояние и выполняют команды, а WebSocket передаёт изменения статусов и координат в реальном времени. После разрыва соединения клиент повторно получает актуальное состояние через REST.

### Серверная часть

Сервер реализован на FastAPI. Он отвечает за валидацию входных данных, расчёт стоимости, переходы статусов, проверку прав, сохранение данных и публикацию событий. Критичные правила должны выполняться на сервере и не могут считаться защищёнными только на уровне интерфейса.

### База данных

Основное хранилище — PostgreSQL. Схема нормализована до третьей нормальной формы. В ней предусмотрены отдельные справочники ролей, услуг, статусов и категорий, связи пользователей и ролей, адреса, заведения, меню, тарифы, заказы, позиции заказа и история статусов.

Для пространственных операций в целевом варианте может использоваться PostGIS. Версия тарифа должна сохраняться в заказе или аренде, чтобы последующий пересчёт не менял уже оформленную операцию.

## Бизнес-сценарии

### Такси и доставка

1. Клиент выбирает услугу, адреса и дополнительные параметры.
2. Сервер проверяет данные, маршрут, тариф и доступность исполнителей.
3. Сервер рассчитывает стоимость и создаёт заказ.
4. Оператор или алгоритм назначает исполнителя.
5. Заказ проходит согласованные статусы: создание, назначение, принятие, выполнение, завершение или отмена.
6. История статусов сохраняется, а после завершения клиент может оставить отзыв.

Доставка использует каталог заведений, меню и состав заказа. В `order_items` сохраняются цена и название позиции на момент покупки, чтобы изменения меню не меняли историю заказа.

### Аренда самоката и велосипеда

1. Клиент видит доступную технику и геозоны на карте.
2. Клиент бронирует объект.
3. Система проверяет, что у клиента нет конфликтующей активной аренды и техника свободна.
4. QR-разблокировка выполняется в учебном режиме.
5. При начале аренды фиксируются техника, тариф и время.
6. При завершении проверяется разрешённая зона парковки и рассчитывается стоимость.

Статусы техники и статусы аренды ведутся раздельно. Это позволяет отличать свободную, забронированную, используемую и обслуживаемую технику от состояния конкретной аренды.

## API и события

Основные текущие endpoints прототипа:

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка доступности API |
| `GET` | `/api/config` | Конфигурация клиентской части |
| `GET` | `/api/restaurants` | Список заведений и меню |
| `GET` | `/api/orders` | Получение заказов |
| `POST` | `/api/orders` | Создание заказа |
| `PATCH` | `/api/orders/{id}/status` | Допустимый переход статуса |
| `GET` | `/api/couriers` | Получение исполнителей |
| `POST` | `/api/trace/{performer_id}` | Обновление позиции исполнителя |
| `GET` | `/api/geocode?q=...` | Поиск адреса через Nominatim |
| `GET` | `/api/reverse-geocode?lat=...&lng=...` | Получение адреса по координатам |
| `GET` | `/api/routes?...` | Расчёт автомобильного маршрута через OSRM |
| `WS` | `/ws` | События заказов и движения исполнителя |

В WebSocket используются события `orderCreated`, `orderStatusUpdated` и `driverMoved`. Сначала событие сохраняется в базе, затем публикуется подписчикам. Это позволяет восстановить состояние через REST при потере соединения и избежать зависимости от одного сообщения WebSocket.

API-документация FastAPI доступна по адресу `/docs` после запуска сервера.

## Структура данных

Ключевые сущности целевой модели:

- `users`, `roles`, `user_roles` — пользователи и разграничение доступа;
- `sessions` — активные сессии;
- `addresses` — нормализованные адреса и координаты;
- `service_types` — такси, доставка, самокат и велосипед;
- `restaurants`, `menu_categories`, `menu_items` — каталог и меню;
- `tariffs` — правила и версии тарифов;
- `orders`, `order_items` — заказы и их состав;
- `order_statuses`, `order_status_history` — текущие статусы и история переходов;
- сущности техники, бронирований, аренд и геозон — для сервиса проката;
- сущности аудита и аналитики — для администрирования и показателей.

SQL-источники схемы:

- [000_create_database.sql](server/fastapi/migrations/000_create_database.sql) — создание базы `yago` при обычной установке PostgreSQL;
- [001_er_model.sql](server/fastapi/migrations/001_er_model.sql) — таблицы, связи, ограничения и начальные справочники;
- [yago-er-3nf.drawio](docs/week-03/p3/yago-er-3nf.drawio) — логическая ER-модель в diagrams.net.

## Запуск локально

Требования: Node.js 20+, Python 3.11+ и Docker Compose.

```bash
npm install
python3 -m venv server/fastapi/.venv
source server/fastapi/.venv/bin/activate
pip install -r server/fastapi/requirements.txt
cp server/.env.example server/.env
docker compose up -d db
npm run dev
```

После запуска:

- клиент: <http://localhost:5173>;
- API: <http://localhost:8000>;
- OpenAPI: <http://localhost:8000/docs>;
- PostgreSQL: `localhost:5432`, база `yago`, пользователь `yago`.

PostgreSQL хранит данные в Docker volume `yago-postgres`. Для остановки контейнера:

```bash
docker compose down
```

Данные volume при этом сохраняются.

### Настройка окружения

Скопируйте [server/.env.example](server/.env.example) в `server/.env` и настройте:

- `DATABASE_URL` — подключение к PostgreSQL;
- `CORS_ORIGINS` — разрешённые адреса клиента;
- `NOMINATIM_BASE_URL` и `NOMINATIM_USER_AGENT` — геокодирование;
- `OSRM_BASE_URL` — маршрутизация;
- `TAXI_BASE_FARE` и `TAXI_PRICE_PER_KM` — тариф такси.

Файл `.env` и реальные секреты нельзя добавлять в репозиторий.

При обычной установке PostgreSQL базу и таблицы можно создать так:

```bash
psql -U postgres -f server/fastapi/migrations/000_create_database.sql
psql -U yago -d yago -f server/fastapi/migrations/001_er_model.sql
```

## Внешние сервисы и ограничения

YaGo использует OpenStreetMap-совместимые сервисы:

- Nominatim — поиск адресов и обратное геокодирование;
- OSRM — автомобильный маршрут, геометрию улиц, расстояние и ETA.

Публичные endpoints имеют ограничения по частоте, доступности и правилам использования. Для production-развёртывания следует использовать собственные экземпляры сервисов или согласованный коммерческий API и соблюдать условия лицензирования и атрибуции.

В учебном варианте:

- оплата эмулируется;
- физическая разблокировка замка эмулируется QR-командой;
- 2FA и проверка студенческого статуса могут работать без внешнего провайдера;
- PostGIS и геозоны подключаются в части проекта, где они нужны для пространственных проверок.

## Критерии готовности

Проект считается принятым, когда:

- каждый сценарий содержит входные данные, результат, ошибки, роль, состояния и используемые сущности;
- ERD, DFD, IDEF, API-контракты и код используют согласованные термины и статусы;
- регистрация, такси, доставка и аренда проходят путь от интерфейса до базы данных;
- запрещённые действия отклоняются сервером;
- суммы и переходы статусов рассчитываются и проверяются сервером;
- миграции разворачивают базу с нуля, а история сохраняется после перезапуска;
- WebSocket-трекинг показывает только разрешённые данные и восстанавливается через REST;
- повторные запросы и обрыв соединения не создают дублирующиеся заказы;
- явно указано, где используется реальная интеграция, а где учебная эмуляция;
- инструкции запуска, диаграммы, пояснительная записка и демонстрационные сценарии соответствуют фактическому состоянию приложения.
