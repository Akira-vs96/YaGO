# П3. Черновой список сущностей базы данных

[Все материалы недели](../../README.md) · [Қазақша](../kk/03-database-entities.md)

Версия: 1.0, неделя 2. Ответственный: П3 — Orders & Business Logic. Получатель: П5 — Admin Panel & Analytics.

Документ фиксирует информационные объекты будущей системы YaGo для Астаны. Это задание на проектирование, а не описание созданной базы: сейчас бизнес-данные живут в массивах Node.js, а PostgreSQL используется только для `SELECT 1` в проверке доступности. Таблиц, миграций и сохранения заказов после перезапуска нет. Связи объектов представлены в [ER-модели П5](../../p5/ru/05-er-model.md); жизненный цикл аренды — в [спецификации П4](../../p4/ru/04-scooter-specification.md).

## 1. Основание и границы

Изучены [план проекта](../../../../TZ_13weeks_team_plan.md), [README](../../../../README.md), [действующий сервер](../../../../server/src/index.js), [модуль заказов](../../../../server/src/modules/orderService.js), [демонстрационные данные](../../../../server/src/data/mockData.js), [конфигурация](../../../../server/src/config.js) и [клиент](../../../../src/App.jsx).

Действующий сервер содержит собственные массивы `restaurants`, `menu`, `couriers`, `orders`. Файлы `mockData.js`, `orderService.js` и `config.js` не импортируются точкой входа, поэтому их содержимое нельзя считать отдельным действующим хранилищем или завершённым слоем бизнес-логики. Источником сведений о текущем API является `server/src/index.js`.

Неделя 2 определяет состав сущностей, назначение атрибутов, словарь и ограничения. Типы колонок PostgreSQL, индексы, миграции, полная детализация геоданных и реализация RBAC относятся к следующим неделям. Имена `snake_case` ниже — согласованные проектные имена, а не уже существующий контракт API.

## 2. Общие решения

- `orders` хранит общий заказ: заказчика, услугу, общий статус, тариф и сумму. Значения `type`: `taxi`, `delivery`, `scooter`, `bike`.
- Для `delivery` поле `delivery_kind` различает `food` и `parcel`. Текущий тип API `food` соответствует будущим `type=delivery`, `delivery_kind=food`. Доставка посылок пока только предусмотрена моделью.
- `rentals` расширяет заказ деталями аренды самоката или велосипеда. Для `taxi`/`delivery` записи аренды нет; для `scooter`/`bike` она ровно одна.
- `performers` объединяет курьеров и водителей: текущий массив `couriers` уже содержит обе категории. Учётная запись пользователя и рабочий профиль исполнителя — разные объекты.
- `vehicles.kind` различает `car`, `scooter`, `bike`. У заказа такси/доставки возможна ссылка `assigned_vehicle_id` на транспорт исполнителя; у аренды техника задаётся только в `rentals.vehicle_id`. Эти ссылки не дублируются для одного заказа.
- `tariffs`, `zones`, `users` общие для модулей. Денежные суммы проектируются как целое число минимальных денежных единиц: `currency=KZT`, 100 тиын = 1 тенге. Вывод в тенге — задача интерфейса.
- Выбранная версия тарифа и её расчётные параметры фиксируются в `orders.tariff_snapshot`. Изменение действующего тарифа не меняет стоимость уже начатой аренды или ранее оформленного заказа.

## 3. Каталог сущностей

В таблице указаны логически необходимые атрибуты. Они ещё не означают окончательный набор колонок и не требуют реализации на неделе 2.

| Сущность | Назначение и черновые атрибуты | Что существует сейчас / что требуется |
|---|---|---|
| `users` | Пользователь: `id`, отображаемое имя, контакт для входа, состояние учётной записи, время создания. Секреты входа хранятся в защищённой форме; конкретный способ входа определяет П1. | Есть только текст `orders.customer` и имена исполнителей. Идентификация заказчика и Auth отсутствуют. |
| `roles` | Справочник полномочий: `code`, название. Коды: `client`, `courier`, `driver`, `restaurant`, `admin`; проектная роль `scooter_operator` обслуживает парк и разбирает инциденты. Управление тарифами/зонами и полный доступ к парку остаются у `admin`. | Первые пять кодов перечислены в конфигурации/UI; контроля прав нет. `scooter_operator` отсутствует в текущем коде. |
| `user_roles` | Назначение роли пользователю: `user_id`, `role_code`. Один пользователь может быть клиентом и исполнителем. | Отсутствует. Повтор одной пары пользователь–роль запрещён. |
| `sessions` | Сессия пользователя: `id`, `user_id`, защищённый идентификатор/хеш токена, создание, срок действия, отзыв. | Отсутствует. Активность определяется сроком действия и отсутствием отзыва. |
| `performers` | Рабочий профиль: `id`, `user_id`, `kind` (`courier`/`driver`), доступность, последняя позиция и время её получения. | `couriers`: `id`, `name`, `role`, `lat`, `lng`, `status`. Нет ссылки на пользователя и времени позиции. |
| `vehicles` | Техника: `id`, уникальный публичный/QR-код, `kind`, состояние, последняя позиция; для электрической техники заряд; для аренды состояние замка и время телеметрии. | Отсутствует. `scooter_tracking` в `featureFlags` не создаёт технику или трекинг. Подробные статусы самокатов/велосипедов задаёт П4. |
| `zones` | Геозона: `id`, имя, `kind` (`service`/`parking`/`no_parking`), геометрия, применимые услуги, признак активности. | Отсутствует. В UI показана карта и точки, но зоны не определены. |
| `tariffs` | Тариф: `id`, код/название, услуга, версия, валюта, начало действия, активность, необязательная сервисная зона. Расчётные параметры зависят от услуги. Для аренды: `unlock_fee_minor`, `price_per_minute_minor`, `reservation_ttl_seconds`. | Отсутствует. Сумма заказа задаётся пользователем или значением по умолчанию. |
| `orders` | Общий заказ: `id`, `customer_id`, `type`, `delivery_kind`, `status`, начало/конец маршрута, `performer_id`, `assigned_vehicle_id`, `restaurant_id`, `service_zone_id`, `tariff_id`, `tariff_snapshot`, `total_minor`, валюта, время создания/завершения и причина отмены. | Есть `id`, текстовый `customer`, `type`, `restaurantId`, `status`, `total`, `start`, `end`, `courierId`, `createdAt`. Нет проверенных связей, тарификации и хранения в БД. Не все проектные поля обязательны для каждой услуги. |
| `restaurants` | Ресторан: `id`, название, кухня, местоположение, активность; необязательный ответственный аккаунт `responsible_user_id`. | Есть `id`, `name`, `lat`, `lng`, `cuisine`, демонстрационное `eta`. Аккаунта ресторана нет. `eta` не является постоянным свойством заведения: оценка зависит от заказа. |
| `menu_items` | Позиция меню: `id`, `restaurant_id`, название, категория, цена, валюта, доступность. | Есть `id`, `name`, `price`, `category` во вложенном словаре `menu[restaurantId]`. Доступность не хранится. |
| `order_items` | Строка заказа еды: `id`, `order_id`, `menu_item_id`, количество, снимок названия, снимок цены за единицу. | Отсутствует. Клиент показывает меню, но корзину и состав заказа не отправляет. |
| `rentals` | Детали аренды: `id`, уникальный `order_id`, `vehicle_id`, статус, `reserved_until`, `started_at`, `finish_requested_at`, `finished_at`, конечная парковочная зона, причина терминального исхода. | Полностью отсутствует. Заказчик, тарифный снимок и сумма берутся из `orders`; отдельные копии не создаются. |

Для простоты первой модели один профиль исполнителя имеет одну категорию, а ресторан — не более одного ответственного аккаунта. Работу одного исполнителя в нескольких категориях и состав сотрудников ресторана можно детализировать позднее; наличие одной лишь роли `restaurant` не должно давать доступ ко всем ресторанам.

## 4. Отображение текущих данных в будущую модель

| Текущий источник/поле | Проектное представление | Правило переноса или пробел |
|---|---|---|
| `orders.customer` | `users.display_name` + `orders.customer_id` | Имя не является уникальным идентификатором. Пользователи создаются/сопоставляются явно, не объединяются автоматически по имени. |
| `couriers.id`, `couriers.name`, `couriers.role` | `performers.id`, `users`, `performers.kind`, `user_roles` | `courier` и `driver` сохраняют смысл. Рабочая категория и разрешение доступа проверяются согласованно. |
| `courierId` | `orders.performer_id` | Для неназначенного заказа ссылка пустая. Текущее автоматическое `c1` не является алгоритмом подбора. |
| `orders.type=food` | `orders.type=delivery`, `delivery_kind=food` | Нормализация при будущей смене контракта; действующий API на неделе 2 не изменяется. |
| `orders.type=taxi` | `orders.type=taxi`, `delivery_kind` пустой | `restaurant_id` и строки еды для такси недопустимы, хотя нынешняя форма отправляет ресторан для обоих типов. |
| `restaurantId`, `menu[restaurantId]` | `restaurants`, `menu_items.restaurant_id`, `orders.restaurant_id` | Ресторан обязателен у доставки еды и отсутствует у других услуг. |
| `start/end`, `lat/lng` | Логические геоточки заказа, ресторана, исполнителя, техники | Координаты проверяются; порядок `[lat, lng]` в Leaflet учитывается при будущей конвертации в геоформат. Точная схема PostGIS — неделя 4. |
| `orders.total`, `menu.price` в тенге | `orders.total_minor`, цена меню/строки в минимальных единицах | При переносе проверяется числовое значение и конвертируется единица. Итог будущего заказа рассчитывает сервер. |
| `createdAt` | `orders.created_at` | Нужны также моменты завершения и отмены; в демонстрационных данных их нет. |
| Текст статуса | Проверяемое состояние и допустимый переход | Сейчас обработчик принимает произвольную строку; предложенный ниже автомат ещё не реализован. |
| `o-${Date.now()}`, `r1`, `c1`, `m1` | Уникальные устойчивые идентификаторы и ссылки | Демонстрационные коды не доказывают уникальность под нагрузкой. Формат ключей определяется при детализации схемы. |
| События `orderCreated`, `orderStatusUpdated`, `driverMoved` | Уведомления об изменении объектов | События не заменяют сохранение в БД. Клиент после переподключения читает актуальное состояние. |

Из демонстрационных заказов нельзя восстановить состав еды, тариф, фактическое время поездки, оплату и завершение: этих сведений нет. Начальные точки заказов еды также не гарантированно совпадают с рестораном; при подготовке seed-данных их нужно согласовать явно.

## 5. Состояния и общие ограничения

### Заказ и исполнитель

Общий словарь заказа: `pending`, `assigned`, `in_progress`, `completed`, `cancelled`. Для такси/доставки основной путь — `pending → assigned → in_progress → completed`; отмена возможна по правилам услуги с сохранением причины. Терминальный заказ не возвращается в работу. Для аренды состояние общего заказа является проекцией `rentals.status`, а этап `assigned` не используется.

В текущих данных встречаются `assigned` и `in_progress`, новые заказы получают `pending`; остальные значения — проектные. Доступность исполнителя: `available`, `busy`, проектный `offline`. Выделенный исполнитель должен иметь подходящую категорию и не быть занят другим несовместимым заказом. Модель недели 2 предполагает один активный заказ на исполнителя; пакетные доставки относятся к расширениям.

### Аренда и техника

| `rentals.status` | Смысл | `orders.status` |
|---|---|---|
| `reserved` | Техника забронирована до срока | `pending` |
| `unlocking` | Ожидается подтверждение разблокировки | `pending` |
| `active` | Поездка начата | `in_progress` |
| `finishing` | Запрошено завершение, ожидается подтверждение | `in_progress` |
| `completed` | Завершение подтверждено | `completed` |
| `cancelled` | Отмена до начала | `cancelled` |
| `expired` | Срок брони истёк | `cancelled` |
| `failed` | Отказ запуска до начала поездки | `cancelled` |

Состояния техники для `scooter`/`bike`: `available`, `reserved`, `in_use`, `maintenance`, `charging`, `offline`; для обычного велосипеда `charging` неприменим. Потеря связи в активной аренде фиксируется отдельно и не освобождает технику. Доступность автомобилей для назначения определяется профилем исполнителя; полный автомат состояния автомобилей в этой версии не задаётся.

Обязательные бизнес-ограничения для будущей реализации:

1. Все ссылки ведут на существующие объекты. Заказ привязан к реальному заказчику; изменение имени не изменяет историю заказов. Исторические записи не удаляются каскадно вместе с аккаунтом, рестораном или тарифом.
2. Назначение исполнителя, бронирование техники и переходы состояний выполняются согласованно. Проверка доступности и запись брони должны быть одной атомарной операцией.
3. Для `scooter`/`bike` существует ровно одна аренда с соответствующей категорией техники; у такого заказа нет исполнителя, ресторана, строк еды и `assigned_vehicle_id`.
4. У пользователя и единицы техники одновременно не более одной аренды в состояниях `reserved`, `unlocking`, `active`, `finishing`. Терминальный исход освобождает ресурс только после проверки фактического состояния техники.
5. `failed`, `cancelled`, `expired` применяются к аренде до старта и не создают начисление. Ошибка после старта не превращает начатую поездку автоматически в бесплатную или завершённую; она требует подтверждённого завершения/операторского решения по спецификации П4.
6. Заказ еды содержит хотя бы одну строку с положительным целым количеством. Все позиции относятся к выбранному ресторану. Название и цена в строке фиксируются на момент оформления.
7. Денежные значения неотрицательны, имеют единую валюту заказа, итог рассчитывается по зафиксированным параметрам. Для такси/доставки `pending` может содержать оценку; при завершении фиксируется окончательный итог. Для аренды до старта начисление нулевое.
8. Позиции должны быть корректными географическими координатами; временные отметки — сопоставимыми. Начало аренды не позже её подтверждённого конца. Актуальность телеметрии проверяется перед выдачей техники.
9. Завершение аренды допустимо в активной парковочной зоне внутри разрешённой сервисной территории и вне `no_parking`. Запрет парковки имеет приоритет при пересечении зон. Геопринадлежность проверяется по координате, а не только по переданному клиентом идентификатору зоны.
10. Роли определяют полномочия, а связи с конкретными заказами/ресторанами — область доступа. Проектные ограничения должны обеспечиваться сервером и, где возможно, БД; в текущем MVP они не обеспечены.

## 6. Передача П5 и дальнейшее развитие

П5 получает 13 согласованных сущностей, единый словарь типов/статусов и правила обязательности связей. [Первая ER-модель](../../p5/ru/05-er-model.md) использует те же имена. Числовые ставки, время брони и критерии допуска техники — в [спецификации аренды](../../p4/ru/04-scooter-specification.md); они являются учебными параметрами, а не рыночными тарифами.

На неделе 3 уточняются обязательность атрибутов и случаи переназначения исполнителя. На неделе 4 выбираются физические ключи, ограничения, миграции и геотипы. Необходимые точки расширения: история статусов/назначений, точки трека, платежи/возвраты, подтверждение студенческого статуса и скидки, отзывы, журнал действий оператора, сотрудники ресторанов и обслуживание техники. Эти объекты не выдаются за реализованные и не включаются в основной контур ERD V1 без соответствующих сценариев.
